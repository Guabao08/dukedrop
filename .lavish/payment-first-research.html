DUKEDROP · PAYMENT FLOW

Make payment the gate to fulfillment details

Brainstorm and research brief · October 6, 2026. The aim is a paid order before anyone enters dorm, room, tracking, or pickup details—and a clear way to tell paid, abandoned, and unfinished apart.

What’s happening now

The order desk asks for the full set of operational details, saves an order as unconfirmed, then hands the customer to Venmo/Zelle or the embedded Stripe payment form. So the database already receives unpaid requests; the manual payment methods can also be left without any confirmation signal in the site. Stripe itself is integrated, but its checkout currently starts after the full form.

Proposed customer journey

1Choose service & quantity

Use only the selections needed to calculate the amount and validate any promo.

2Pay securely

Create a short-lived payment attempt linked to an internal order ID. Show the final price.

3Unlock the form

After verified payment, return to a signed, resumable link for dorm, room, contact, and package details.

4Complete or follow up

Show “paid · details needed” until submitted; send a receipt/link and remind if unfinished.

Important split: the success redirect improves the customer journey; the server-side Stripe webhook is the source of truth for marking paid. Stripe explicitly advises listening for webhook events because relying on the landing page alone is unreliable.

Ways to do this

Best fit · reuse what exists

Stripe first, then the DukeDrop form

Keep your current price calculator and Stripe Checkout integration; reorder the journey.

  • Pre-payment screen: service, quantity, promo, contact email/phone as needed.
  • Pay with Stripe; attach internal order ID to the Checkout Session.
  • Webhook records payment; success page returns with a one-time/resumable form token.
  • Dashboard separates paid / needs details, abandoned checkout, and complete.
Work: moderate code change. Lowest workflow/tool disruption; card fees apply. Stripe fee depends on your account/pricing.
Fast setup · less control

Form platform with required payment

Evaluate Jotform with Stripe, Square, or another supported processor.

  • One hosted flow can collect fields and payment.
  • Could use a tiny pre-payment order form, then payment, then second form.
  • Check conditional redirects, unique order IDs, webhook/export quality, and plan limits before migrating.
Work: low to moderate setup, recurring platform cost and vendor dependence. Verify that its flow truly blocks fulfillment fields until payment.
Alternative processor

Square Checkout / Payment Links

Useful if Square’s checkout experience or in-person operations matter.

  • Hosted payment links support custom fields and post-checkout redirects.
  • API-generated links can carry an order and return to a custom site.
  • Still requires reliable event-to-order reconciliation and a gated form page.
Work: moderate integration. It does not remove the need for the post-payment form and paid-state handling.

My recommendation

Run a focused Stripe-first pilot and make card checkout the only route that can create a fulfillment-ready order. Build an unpaid “checkout attempt” record containing only pricing inputs; create/activate the operational order only after the signed webhook confirms payment. Then show an order-specific completion page with a resume link. Keep Venmo/Zelle only as a temporary staff-confirmed exception if customers need them; label these “payment pending verification” and never treat a return click or screenshot as proof.

Questions that shape implementation

DecisionPractical starting pointWhy it matters
Must every method be prepaid?Yes for self-serve fulfillment; manual methods need staff verification or should be removed.Venmo/Zelle transfers do not naturally provide the same application-level confirmation path as a Stripe Checkout webhook.
How much before payment?Only service, quantity, promo, and perhaps email/phone.Pricing requires some input; keep sensitive/logistical details behind payment.
If they pay then leave?Persist paid + details incomplete; provide emailed/SMS resume link and dashboard queue.Payment success and form completion are separate states.
What about failed/abandoned payment?Keep a short-lived attempt and allow retry; expire/cancel stale attempts.A started Checkout Session is not a paid order.
What if price/details change?Lock quoted price at payment; handle later scope changes as a staff-reviewed adjustment.Avoid charging one amount and silently editing the order into another.

Build sequence

1 · Pilot policy

Choose card-only for self-serve and define whether manual transfers remain exceptions.

2 · Split the data model

Represent checkout attempt, paid status, details-needed status, and completed order distinctly.

3 · Gate by server proof

Webhook confirms payment; signed token grants access to the right order form. Never trust a client URL alone.

4 · Recover abandonment

Capture contact before payment if appropriate; offer retry and resume links; measure each funnel stage.
