DevilDrop · Stripe checkout

A step by step implementation path

The app already has the core Stripe path: order creation, server-calculated Checkout Sessions, an embedded form, and a signed webhook that can mark an order paid. This guide shows how to finish, verify, and launch that path safely.

Where the app stands

Already in code

Order & amount

api/orders.js calculates totals on the server and saves the order. The checkout endpoint recalculates the amount from saved order data and creates the Checkout Session with inline price_data; there is no fixed Stripe Price ID to configure.

Already in code

Payment confirmation

api/stripe-webhook.js verifies Stripe’s signature against the raw request body, checks the saved order and amount, and conditionally marks it paid.

Already in code

Browser flow

app.js saves the order first, requests the client secret from the server, then mounts and confirms Stripe’s form. The secret key stays server-side.

Decision before launch

Checkout interface

The current code uses Stripe’s custom Checkout Form preview beta and a preview API version. Confirm the preview’s production terms and support expectations in the Stripe account. For the lowest maintenance, consider Stripe-hosted Checkout or stable embedded Checkout instead.

Ignore the stale setup steps in STRIPE_INTEGRATION_TODO.md that ask for a fixed Price ID or say there is no webhook. Those statements don’t match the current endpoint code.

Implement and verify it in this order

  1. Choose the Checkout UI. Decide whether to keep the custom form preview already in index.html, app.js, and api/create-checkout-session.js, or move to stable embedded/hosted Checkout. If staying on preview, pin and verify its Stripe API/JS version in test mode, then explicitly confirm its launch support status with Stripe.
  2. Keep pricing authoritative on the server. Preserve totalFor() in api/orders.js and the second total check in api/create-checkout-session.js. Never accept an amount or discount from the browser as the amount to charge. Keep zero-dollar orders out of Checkout, as the current UI does.
  3. Set up separate test and live secrets. In local environment and Vercel, configure STRIPE_SECRET_KEY, STRIPE_PUBLISHABLE_KEY, and STRIPE_WEBHOOK_SECRET, plus ORDER_STORAGE_ENABLED=true, SUPABASE_URL, and SUPABASE_SERVICE_ROLE_KEY. Use matching test keys locally and matching live keys in production. Only the publishable key may be returned by /api/config; keep secrets out of source control and browser code.
  4. Register the webhook in Stripe test mode. Point it at https://<your-test-host>/api/stripe-webhook (or forward Stripe CLI events to local dev). Subscribe to checkout.session.completed. If you allow delayed payment methods, also handle their async success and failure lifecycle. Copy that endpoint’s whsec_... into STRIPE_WEBHOOK_SECRET; each endpoint/environment has its own secret.
  5. Decide which methods are enabled. The UI offers “Card” only. Restrict Checkout to card if that is the intended promise, or make sure all methods enabled in Stripe Dashboard have correct pending, asynchronous success, and failure handling. The current webhook handles completed and async success, but doesn’t record async failure for dashboard/customer messaging.
  6. Prevent duplicate sessions. The browser disables controls while starting checkout, but a retry or second request can still create another session for one order. Add a server-side Stripe idempotency key derived from the saved order ID, and consider persisting the Checkout Session ID so support can find the exact attempt.
  7. Test the complete journey in test mode. Place one order for each service, quantity tier, and promo case; verify the Stripe amount equals the displayed and saved amount. Test successful card payment, a declined card, 3DS authentication, refresh/retry, duplicate webhook delivery, invalid webhook signature, and a zero-dollar order. Confirm the order changes to paid only after Stripe’s webhook succeeds. The browser success message currently says staff will confirm; update it to match automatic webhook confirmation.
  8. Reconcile and monitor. Confirm the Stripe Dashboard shows the test payment and webhook delivery. Add a way to spot payments where Stripe says “paid” but the database update failed, such as retry monitoring and a daily reconciliation/support procedure. Check that refunds in Stripe are reflected in the app; today webhook code doesn’t handle refund events.
  9. Launch live with a small verification. Add a separate live webhook endpoint and live secrets, deploy, make a small real payment, verify it in Stripe and the dashboard, then refund it. Make sure refunds and customer support procedures are ready before promoting card checkout.
